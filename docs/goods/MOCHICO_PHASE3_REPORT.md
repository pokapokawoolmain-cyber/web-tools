## 3. RLS 変更内容
- **緩めた所はなし**
- 新テーブル（カテゴリ・画像・絵柄）: 閲覧 = メンバー（`goods_is_member`）、作成・変更・削除 = オーナー（`goods_is_owner`）。anon は権限なし
- 列権限を追加で絞った: `goods` はクライアントから `image_path / thumb_path / kind` を書けない（代表画像はトリガー、種類の変更は変換 RPC のみ）。`goods_images` は `sort_order` だけ更新可、`goods_variants` は名前・画像・並び順だけ更新可
- 所持（数量）は従来どおり本人だけ。絵柄の行も同じポリシー（他人の数量は SELECT / UPDATE できないことをテストで確認）
- 画像パス: 他イベントのフォルダ・`..` を含むパスは DB が拒否

## 4. 検索機能の仕様
- 対象: 商品名の部分一致。全角/半角・大文字/小文字・ひらがな/カタカナの違いを無視（「ぺんらいと」で「ペンライト」が見つかる）。スペース区切りは AND
- 入力と同時に更新（`useDeferredValue` で入力の操作感を優先）。クライアント側処理（1イベント最大1000件）
- 所持（すべて / 未取得 / 取得済み）× カテゴリ × 並び替え（登録順・名前順・価格の安い順・高い順。価格未定は常に最後、同額は名前順）を併用可
- 0件のときは「条件に合うグッズはありません」＋「検索・カテゴリの条件をクリア」
- 取得率（上部の進捗）は常にイベント全体。所持タブの件数は検索・カテゴリで絞った範囲
- 画面を圧迫しない工夫: 検索・並び替えは **グッズ8件以上のイベントだけ**表示、カテゴリのタブは **カテゴリがあるときだけ**（オーナーには「カテゴリを追加」）。少ないイベントは従来と同じ画面
- 並び替え・カテゴリはイベントごとに端末へ記憶（所持タブは従来どおり）

## 5. カテゴリ機能の仕様
- イベント単位の共有情報。参加者全員に同じタブが表示される
- 横スクロールのタブ: すべて ／ 各カテゴリ（件数）／ 未分類（未分類のグッズがあるとき）
- オーナー: 追加（候補9種をワンタップ、自由入力も可）・名前変更・並び替え・削除。削除してもグッズは残り未分類になる（確認ダイアログで件数を表示）
- メンバー: 閲覧と絞り込みのみ（編集ボタンは表示されず、DB でも拒否）
- グッズ登録フォーム: カテゴリをチップで選択、その場で新しいカテゴリも作れる
- 既存データ: 既存の文字列カテゴリからカテゴリを自動作成し、グッズを紐づけ（ローカルの既存データで 14 カテゴリ・106 グッズを確認、名前の不一致 0）

## 6. 数量管理の仕様
- 数量は 0〜9999 の整数。0 = 未取得、1 以上 = 取得済み。負数・小数・文字・1万以上は UI でも DB でも拒否
- カードのタップ（従来のワンタップを維持）: 0 → 1、1 → 0（トーストで元に戻せる）
- **2個以上のカードはタップしても減らない** → 数量シートが開く（カードに「×2」、読み上げも「取得済み2個。タップで数量を変更」）
- 数量シート: −／数値（直接入力）／＋。数値欄は確定時（Enter・フォーカスを外す）に検査し、不正なら元の値へ戻してエラー表示
- 連打・通信競合: 対象ごとに書き込みを直列化し、最後の値だけ保存。失敗時は最後に確定した数量へ戻してエラー表示
- ランダム商品: 絵柄ごとに数量。商品の合計 = 絵柄の合計、商品の「取得済み」= 合計1以上。カードに「全8種」／取得後は「2/8種」と「×3」
- 他ユーザーの数量は閲覧・変更不可（作成者にも見えない）

## 8. UI 変更箇所
- イベント画面: 進捗（変更なし）の下に、所持タブ（変更なし）＋検索・並び替え（8件以上）＋カテゴリタブ（カテゴリありの時）を上部固定でまとめて配置
- グッズカード: 2個以上で「×N」、ランダムは「全8種／2/8種」バッジと合計、画像が2枚以上なら「N枚」。読み上げ文も状態に合わせて変更
- 詳細シート: 画像ギャラリー（横スワイプ・ドット表示）、通常商品は所持数の −／数値／＋、ランダム商品は「絵柄ごとの所持数」一覧（ギャラリーとは別の区画）
- カテゴリ編集シート（オーナー）
- グッズ登録・編集フォーム: 写真（最大10枚・複数選択・並び替え・代表設定・削除）、種類（通常／ランダム）、絵柄（追加・まとめて追加・名前・画像・並び替え・削除）、カテゴリのチップ選択と新規作成。失われる操作は保存前に確認
- 共有ページ（未ログイン閲覧）: ランダム商品の「全N種」と絵柄一覧
- 確認ダイアログの見出し id を一意化（1画面に複数あると読み上げ名が混ざる既存の問題を修正）

## 10. 既存機能への影響
- 少ないイベント（8件未満・カテゴリなし）の画面は従来と同じ。ワンタップの取得切り替え・元に戻す・所持タブ・オフライン表示・共有・退会は既存テストどおり動作
- 共有の安全設計（token → HttpOnly Cookie → token なし URL）、所持情報の非公開、退会時の保全は変更なし
- CEO Dashboard の集計: `status='owned'` は数量から自動で決まるため動作は変わらない。ただし「owned_marks」はランダム商品の絵柄ごとの行も1件ずつ数える（意味が少し変わる）
- `goods_my_events` の取得数は「数量1以上のグッズの数」に（ランダム商品の絵柄で重複して数えない）
- 旧クライアント（デプロイ時に開いたままの画面）は所持の更新・画像付き保存がエラーになり、再読み込みで解消

## 11. 本番反映手順（承認後）
1. 本番 DB のバックアップ（Supabase の PITR／日次バックアップの確認）

4. main へマージ → toolbox-jp が Production デプロイ（DB とアプリの間の数分間、旧画面からの所持更新はエラー表示になる）
5. Production で E2E 相当の確認（検索・カテゴリ・数量・ランダム・複数画像・共有・退会・390px）。テストデータは削除
6. 問題があれば: アプリを直前のデプロイへ Instant Rollback → 必要ならロールバック SQL（失われる情報は §7）

## 12. 残存リスク
- 旧クライアントの一時的なエラー（デプロイ直後に開いたままの画面）
- ランダム商品の絵柄削除・ランダム→通常の変換は、共有している全員の絵柄ごとの数量に影響する（保存前に確認ダイアログで明示）
- 変換で移した所持行の `acquired_at` は変換時刻になる
- 共有ページ（未ログイン閲覧）は代表画像と絵柄だけを表示（2枚目以降のギャラリーは参加後の画面で表示）
- Storage 容量: 1枚あたり約 56KB（full 46KB + thumb 10KB の本番実測）。上限いっぱい（1000グッズ × 10枚 ＋ 絵柄）で 1イベント最大約 600MB。通常の利用では数十MB程度。グッズの論理削除では画像は残る（既存仕様。イベント削除・孤児掃除で消える）
- 実機（iPhone Safari・ホーム画面モード）での確認は未実施（ローカルのモバイル幅・Chrome で確認）。横スワイプのギャラリーと数値入力は実機での確認を推奨
