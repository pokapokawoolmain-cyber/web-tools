## 1. 既存 DB 構造（調査結果）

| テーブル | 関係する列 | 備考 |
|---|---|---|
| `events` | `start_date date`, `end_date date`（**開催日**）, `description` | 開催日は日付のみ。今回は**使わない・変更しない** |
| `goods` | `name`, `price`, `description`, `category`, `kind` 等 | 日付の列は無い |
| 権限（RLS） | events: オーナーのみ更新 / goods: イベントのオーナーのみ追加・更新 / 参加者（member）は閲覧のみ | 既存の方針をそのまま使える |
| 列権限 | **未適用の contract（20261009）が goods の書き込み可能な列を限定する** | 新しい列を contract の許可リストに追加しないと、contract 適用後に保存できなくなる（§3-4） |
| イベント一覧 | RPC `goods_my_events()` が一覧の行を返す | 期限を返すには戻り値の型を変える（DROP → CREATE が必要） |
| 共有ページ | `goods_get_shared_catalog()`（jsonb） | キーの追加は既存アプリに影響しない |
| 表示用の日付 | `lib/goods/format.ts` は端末のタイムゾーンで日付を扱う | 期限判定には使わない（日本時間で計算する新しい関数を作る） |

## 2. 日時の保存方式

### 方針: 「日本時間の日付」と「時刻（任意）」を別々の列に保存する

| 項目 | 列（events・goods 共通の名前） | 型 |
|---|---|---|
| 予約開始 | `reserve_start_date`, `reserve_start_time` | `date`, `time`（null = 時刻なし） |
| 予約終了 | `reserve_end_date`, `reserve_end_time` | 同上 |
| 販売開始 | `sale_start_date`, `sale_start_time` | 同上 |

理由:
- **「日付だけ」か「日付＋時刻」かがデータで明確**（time が null なら日付のみ）。timestamptz に入れると、日付だけの指定と「0:00 指定」の区別がつかない
- **日本時間で入力された値をそのまま保存**するので、端末や DB のタイムゾーン設定に左右されない
- 日本には夏時間が無いため、比較用の時刻は常に `日付 + 時刻 + 09:00` で一意に決まる

### 期限の判定ルール（すべて日本時間）

| 項目 | 時刻あり | 日付のみ |
|---|---|---|
| 予約開始 | その時刻から受付 | その日の **0:00** から |
| 予約終了 | その時刻の**直前まで**受付（その時刻ちょうどで終了） | その日の **23:59 まで**受付（翌日 0:00 で終了）※D2 |
| 販売開始 | その時刻から販売 | その日の 0:00 から |

### DB の制約（壊れたデータを保存させない）
- 時刻だけの入力は不可（`*_time` は `*_date` があるときだけ）
- 予約の開始と終了が両方あれば、**終了 ≥ 開始**（上の判定ルールで比較）
- 販売開始と予約の前後関係は制約しない（事後通販などで販売が先・後どちらもあるため）

## 3. スキーマ変更（expand のみ・既存データは変更しない）

Migration 案: `20261011000000_mochico_schedule.sql`

### 3-1. 列の追加（すべて null 可・既定値なし）
- `events`: 上記 6 列
- `goods`: 上記 6 列 ＋ `schedule_override boolean not null default false`（D1:「このグッズだけ別に設定」）
- 既存の行はすべて「未設定」のまま。**既存イベント・グッズの表示や動作は変わらない**

### 3-2. 有効なスケジュール（継承）を返す関数
- `goods_effective_schedule(goods)` … `schedule_override` が true ならグッズの列、false ならイベントの列
- 一覧・並び替え・共有ページで同じルールを使う（アプリ側にも同じ純粋関数を置き、テストで一致を確認）

### 3-3. RPC の更新
- `goods_my_events()`: 戻り値にイベント自身のスケジュール 6 列と `goods_schedule_count`（個別のスケジュールを持つグッズ数、D3 の補足用）を追加
  - 戻り値の型が変わるため `drop function` → `create function`（1トランザクション内。旧アプリは名前で項目を読むので影響なし）
- `goods_get_shared_catalog()`: イベントとグッズに有効なスケジュールを追加（D4。所持情報は含めない）

### 3-4. 権限
- 書き込みは**イベントのオーナーだけ**（既存の RLS のまま）。参加者は閲覧のみ・変更は API でも不可
- **contract（20261009、未適用）でスケジュールの列権限が失われないようにする**: テーブル単位の revoke は列単位の許可も外すため、contract の末尾で「列があれば」スケジュールの 7 列を許可し直す（DO ブロック）。schedule 側でも列単位で許可するので、**どちらの順番で適用しても書ける**（ローカルで 3 通りの順序を検証済み）。contract の適用は従来どおり別途承認
- `schedule_override` を false に戻したときにグッズの列を消すかは、**消さずに残す**（もう一度「別に設定」にすると前の値が戻る。表示・判定には使わない）

### 3-5. 互換性
| 対象 | 影響 |
|---|---|
| 既存データ | 列追加のみ・値は null。表示は変わらない |
| 旧アプリ（デプロイ前後） | 新しい列を読まない・書かない。RPC の追加項目は無視される |
| オフラインキャッシュ（IndexedDB） | 新しい項目は任意。古いキャッシュは「未設定」として表示 |
| contract 適用後 | 列リストに追加済みなら保存できる（§3-4） |

## 4. 状態の判定と表示文言

### 状態
| 状態 | 条件 |
|---|---|
| 予約前 | 現在 < 予約開始 |
| **受付中** | 予約開始 ≤ 現在 < 予約終了（開始が未設定なら、終了前はすべて受付中） |
| 受付終了 | 現在 ≥ 予約終了 |
| （表示なし） | 予約の開始・終了がどちらも未設定 |

販売開始は別の小さな表示（「販売 10/20〜」「販売中」）。

### 残り時間の表示
| 残り | 表示例 |
|---|---|
| 2日以上 | 「あと3日」（日本時間の暦日で数える） |
| 日付のみの最終日 | 「今日まで」 |
| 時刻あり・24時間未満 | 「あと5時間」、1時間未満は「あと45分」 |
| 予約前 | 「10/20 10:00〜」 |
| 受付終了 | 「予約終了」 |

色だけで区別しない（アイコン＋文字）。受付中で残り3日以内は強調色。

現在時刻は端末の時計を使う（表示のみ。保存や権限には使わない）。

## 5. UI 設計

### 5-1. イベント一覧
- 既存の「開催日」の行とは**別の行**に、予約の状態を 1 つだけ表示（アイコンも別: 開催 = カレンダー、予約 = 時計）
  - 例: `🕒 予約受付中・あと3日（10/15 23:59まで）`／`🕒 予約 10/20 10:00〜`／`予約終了`（灰色）
- グッズ固有の期限があるときは「個別の予約期限あり（n件）」の補足だけ（D3。イベントの期間として表示しない）
- 並び替えに「**予約期限が近い順**」を追加（受付中 → 予約前 → 設定なし → 受付終了）。既定は従来どおり

### 5-2. グッズ一覧（ボード）
- イベント全体の予約状態は**イベントのヘッダーに 1 回だけ**表示（カードごとに同じ表示を繰り返さない）
- カードには、**イベントと違う個別の設定があるグッズだけ**小さな表示（例:「〆10/12」）。情報過多を避ける
- 並び替えに「予約期限が近い順」を追加（既存の検索・カテゴリ・所持の絞り込みと組み合わせ可能）
- 商品詳細シートに予約・販売の詳細と「イベントの設定」／「このグッズの設定」の出どころを表示

### 5-3. 入力画面
- イベント編集・グッズ編集に「予約・販売スケジュール（任意）」の折りたたみ欄
- 各項目: 日付欄 ＋ 時刻欄（時刻は空欄 = 日付のみ）＋「クリア」ボタン
  - iPhone Safari の日付欄は一度入れると空に戻しにくいため、クリアボタンを必ず付ける
  - 既存の日付欄のはみ出し対策（`field.dateInput`）をそのまま使う。2 列に並べず縦に並べる
- グッズ側は最初に「イベントと同じ（10/15 23:59まで）」／「このグッズだけ別に設定」を選ぶ（D1）
- 入力の注意書き:「日本時間」「日付だけの終了日は、その日の 23:59 まで受付」
- 保存前の確認: 終了 < 開始ならエラー表示（DB の制約と同じルール）

### 5-4. iPhone での表示
- 320 / 375 / 390 / 430px で、日付欄・時刻欄・クリアボタンが 1 行に収まり、横にはみ出さないこと
- ネイティブの日付・時刻ピッカーを使う（独自の入力部品は作らない）
- 固定の所持タブ・モーダル・Safe Area など、今回の UI 改善の挙動を崩さない
