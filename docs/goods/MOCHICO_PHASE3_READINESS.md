## 1. 画像アクセスのセキュリティ

### 問題（既存の穴）
`events.cover_image_path` / `goods.image_path` / `thumb_path` に任意のパスを保存でき、共有カタログ（service_role で署名）経由で**他人のイベントの画像を未ログインで表示できた**。ログイン後の画面はユーザー権限で署名するため Storage RLS で拒否されていた。

### 修正（Phase 3 から分離: `20261007000000_mochico_image_path_guard.sql`）
- 保存時の検査（トリガー）: カバーは `{event_id}/cover/`、グッズ画像は `{event_id}/{goods_id}/` 配下のみ。`..` と想定外の文字を拒否。値が変わったときだけ検査（既存行に影響なし）
- 共有カタログ: 規約外のパスは null で返す（既存データに万一あっても署名しない＝多重防御）
- Phase 3 の新テーブル（`goods_images` / `goods_variants`）にも同じ検査を適用（`20261008`）

### 検証結果
| 確認 | 結果 |
|---|---|
| 新規登録: 自分のフォルダは保存可 / 他イベント・別グッズ・`../`・カバーへの他イベント指定は拒否 | ✅ |
| 既存の不正パス（トリガーを無効化して再現）: カタログはカバー・画像とも null | ✅ |
| 実際の共有ページ（未ログイン）: 他イベントのパス・署名URLが HTML に出ない／正当な画像の署名URLは 200 | ✅ |
| ユーザー署名: 自イベントは署名可、他イベントは Storage RLS で拒否（署名・ダウンロード・アップロード） | ✅ |
| **陽性対照**: ガードを外すと同じスクリプトで 5 件失敗（漏えいを再現）→ 適用で 13/13 | ✅ |
| 本番の既存パス（読み取り専用・本日再計測）: カバー 4 / グッズ 39、接頭辞・文字種とも違反 0 | ✅ 既存の正当な画像は壊れない |

### 先行適用の評価: **可能・推奨**
- DB のみの変更（アプリのデプロイ不要）。現行 main のコードでテスト: DB 65/90/68 すべて未修正のまま合格、E2E 34/34（+スマホでは対象外の 1 件）、セキュリティ確認 13/13
- ロールバック SQL あり（データ変更なし）

## 2. Storage 容量

### 画像の処理（コードで確認）
- 端末側で縮小・再圧縮: full 長辺 1600px、thumb 長辺 480px、WebP（非対応端末は JPEG）、品質 0.82 から段階的に下げて **2MB 以下**
- バケット側でも `file_size_limit = 2MB`・MIME は webp/jpeg のみ（サーバーで強制）
- 本番実測（本日）: 86 ファイル・約 10MB、平均 full 185KB / thumb 43KB（1 枚あたり約 **228KB**）、最大 full 595KB

### 上限（DB で強制）
| 単位 | 上限 |
|---|---|
| イベント / ユーザー | 300（既存） |
| グッズ / イベント | 1000（既存） |
| 通常商品 | 写真 10 枚 |
| ランダム商品 | 写真 10 枚 ＋ 絵柄 100（各 1 枚）＝ 最大 110 枚 |
| **画像 / イベント（新設）** | **2000 枚**（写真＋絵柄画像。削除した絵柄の画像も数える。旧アプリ経由の保存にも適用） |
| カテゴリ / イベント | 50 |

※ 1 枚 = full + thumb の 2 ファイル

### 1 イベントの最大容量と「600MB」に達する条件
以前の「最大 600MB」は誤り（古い 56KB/枚の値を使い、絵柄画像 100 × 1000 グッズを計算に入れていなかった。上限なしでは理論上 11 万枚）。上限 2000 枚を新設した上で:

| 想定 | 1 イベントの最大 |
|---|---|
| 本番平均（228KB/枚）で上限まで登録 | 約 **455MB** |
| 本番最大の写真（595KB＋thumb）ばかりで上限まで | 約 1.4GB |
| 理論上限（全ファイルがバケット上限 2MB） | 約 8GB |

**600MB に達する条件**: 画像が上限の 2000 枚に達し、**かつ**平均が 1 枚 300KB 以上（いまの平均より約 3 割重い）の場合。いまの平均のままなら上限内で 600MB には届かない。

### 不要ファイルの削除・孤立ファイルの回収
| 状況 | 対応 | 確認 |
|---|---|---|
| 写真の削除・差し替え・絵柄画像の差し替え | 保存 RPC が古いパスを返し、端末が Storage から削除 | DB テスト・E2E（保存後 Storage に 4 ファイルだけ残る） |
| アップロード失敗（片方だけ成功を含む） | 端末がその場で両方削除 | コード確認 |
| 保存失敗・途中で閉じた | 日次の掃除（Vercel Cron）が「どこからも参照されていない・1 日以上前」のファイルを削除（**新設**） | DB テスト（1 日未満は対象外・参照中は対象外・ユーザーは呼べない） |
| イベント削除 | 既存の孤児掃除がフォルダごと削除 | 既存テスト |
| 絵柄の削除 | 論理削除のため画像は**残す**（戻せるように） | — |
| **本番での影響（読み取り専用の模擬実行）** | 86 ファイル中、新しい掃除が消す対象は **0** | ✅ |

## 3. 所持データ保護

| 操作 | 以前の実装 | 今回 |
|---|---|---|
| 絵柄の削除 | 物理削除 → 参加者の数量も消えた | **論理削除**。数量は残り合計から外れるだけ。編集画面の「削除した絵柄」から戻すと数量も戻る。オーナーでも物理削除不可（DELETE 権限なし） |
| ランダム → 通常 | 絵柄の合計にまとめて絵柄を削除 | **共有中（参加者あり）は禁止**（DB で拒否＋画面で選べない）。参加者がいないリストのみ可（表示中の合計を引き継ぐ） |
| 通常 → ランダム | — | 全員の数量を 1 つ目の絵柄へ移す（失われない） |
| 種類の直接変更 | 列権限で防ぐ予定だった | トリガーでも拒否（変換 RPC 以外では変わらない。contract 前の期間も安全） |
| 共有カタログの変更（カテゴリ削除・名前変更・写真変更） | — | 所持データに触れない（カテゴリ削除 → 未分類、グッズと数量は残る） |
| 旧アプリがランダム商品を「未取得」にする | — | 拒否（絵柄の数量を消さない） |

データ構造: 絵柄ごとの数量は新テーブル `ownership_variants`。`ownerships` は従来どおり (user_id, goods_id) で 1 行、ランダム商品では合計の写し（トリガーで自動更新）。旧アプリは合計（取得済み/未取得）をそのまま読める。

## 5. 本番移行手順

### 構成（3 つの migration）
| 順 | ファイル | 内容 | 旧アプリとの互換 |
|---|---|---|---|
| A | `20261007000000_mochico_image_path_guard.sql` | セキュリティ修正 | ✅ 互換（単独で先行適用可） |
| B | `20261008000000_mochico_phase3.sql`（expand） | 新テーブル・列・トリガー・RPC・既存データの写し | ✅ 互換（旧アプリの書き込みを新構造へ反映） |
| C | `20261009000000_mochico_phase3_contract.sql` | goods の列権限を絞る | ❌ 旧アプリの「グッズ画像の保存」だけ不可 → **新アプリ公開後に適用** |

### 順序と依存関係
```
0. 承認
1. バックアップ ── 2. A（先行リリースでも可）── 3. B ── 4. データ検証 ── 5. アプリデプロイ ── 6. 回帰テスト ── （24時間以上）── 7. C
```
- **B は 5 より前が必須**（新アプリは `ownerships.quantity` と新テーブルを読むため、B が無いと一覧を表示できない）
- **C は 5 の後が必須**（先に適用すると旧アプリの画像保存が失敗）。開いたままの古いタブ・PWA が更新されるまで 24 時間以上あける
- 日次掃除（03:00 JST）と重ならない時間帯に実施

### 各手順
1. **バックアップ**: Supabase の日次バックアップ／PITR の時刻を記録。`pg_dump`（schema ＋ `events` `goods` `ownerships` `event_memberships` `share_links` のデータ）を取得。Storage はファイル一覧（名前・サイズ）を保存。基準値の件数（イベント・グッズ・所持行・取得済み数・画像付きグッズ数）を記録
2. **A**: 適用後、違反 0 件の再確認、共有ページと一覧の画像表示を目視
3. **B**: 1 トランザクションで適用（失敗時は自動で元に戻る）
4. **データ検証**（読み取り専用 SQL）: 基準値と件数が一致／`status='owned'` の件数 = `quantity>0` の件数／画像付きグッズ数 = `goods_images` 件数／カテゴリ文字列のあるグッズはすべて `category_id` あり／`ownership_variants` は 0 件／旧アプリで一覧表示・取得切替が動く
5. **アプリデプロイ**: `feature/mochico-phase3` → `main` マージ（Vercel が自動デプロイ）。READY を確認
6. **回帰テスト**: 本番用テストアカウントで作成→数量→共有→参加→退会の一連（既存の受け入れスクリプトの流れ）。テストデータは最後に削除。**実ユーザーのデータには触れない**
7. **C**: 適用後、新アプリでグッズ登録・写真保存を確認

### ロールバック
| 時点 | 手順 | データ |
|---|---|---|
| 3〜4（デプロイ前） | 通常は不要（B は旧アプリ互換）。戻す場合は `rollback/20261008…_down.sql` | 失われない（Phase 3 のデータがまだ無い） |
| 5〜6（デプロイ後） | **Vercel で直前のデプロイへ戻す（DB はそのまま）**。旧アプリは B の上で動作確認済み | 失われない |
| 7 以降 | `rollback/20261009…_contract_down.sql`（権限を戻すだけ・即時）→ 必要なら Vercel を戻す | 失われない |
| DB も Phase 3 前へ | contract_down → アプリを戻す → `20261008…_down.sql` | 2 枚目以降の写真の登録、絵柄と絵柄ごとの数量、2 個以上の数量（取得済み/未取得に戻る）が失われる → 手順 1 のバックアップから復元可能 |
| A | `20261007…_down.sql`（データ変更なし）。脆弱性が戻るため原則行わない | — |

ローカルで全段のロールバックと再適用を実施して確認済み（Phase 3 のデータがある状態からの down を含む）。

## 7. 残存リスク

1. **古いタブ・PWA（デプロイ後）**: 新アプリで作ったランダム商品を旧画面で切り替えるとエラー表示（データは壊れない）。C の後は旧画面でグッズ写真を保存できない → C を 24 時間以上あけて適用
2. **ユーザー単位の容量上限が無い**（300 イベント × 2000 枚まで可能）。現状 10MB。Storage 使用量の監視を推奨、必要なら後日ユーザー単位の上限を追加
3. **削除した絵柄と画像は無期限に残る**（戻せるようにするため）。上限 2000 枚に含めて数えるので無制限には増えない
4. **DB を Phase 3 前へ戻すと Phase 3 のデータが失われる** → 原則アプリのロールバックで対応し、DB はそのまま
5. **日次の掃除**: 今後、画像パスを別の場所に保存する機能を追加した場合は掃除の条件も更新が必要（現状の本番では削除対象 0）
6. 画像上限 2000 の判定は同時保存で数枚超える可能性（書き込みはオーナーだけのため実害は小さい）
7. 旧アプリで、写真が複数あるグッズの画像を「外す」と、2 枚目が代表に繰り上がる（移行期間中だけ）
